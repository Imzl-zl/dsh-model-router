# Agent Note: 重试次数归每条候选，删掉整请求总上限

Status: implemented

## Context

用户连续三轮提出同一个问题，从"这几层重试是什么关系"收敛到一句：

> "我这么费事的搞这个不就是为了重试切换能正常用……我需要你提前叫停吗？"

原设计有三个数字：`firstHopMaxAttempts`（调用次数）、每条候选的 `maxAttempts`
（调用次数，1..5）、以及 `maxTotalAttempts`（整请求硬上限，默认 3）。它们带来两种
用户可见的混乱：

1. **单位是"调用次数"，语义却是"重试"。** 首发是正常调用，不是重试；用户填 3 以为
   是重试 3 次，实际是"首发 + 2 次重试"。首跳的 1..5 上限与 DSH 自己的
   `retryPolicy.maxRetries`（重试次数，默认 5）比，还少一次且写法相反。
2. **总上限只能"提前叫停"，从不切换、从不增加调用。** 它唯一做的事是截断：截断
   未勾选失败码上 DSH 自己的重试，或截断一条长链走完之前的调用。用户已经把 provider
   的重试次数当成自己配的刹车，这个第三个数字只剩"让人算不明白"的价值——而且它
   允许的调用数还必须由用户自己用 `+1` 和求和算出来。

用户还指出第二件事：插件的每条候选次数对**未勾选切换的错误码**不生效——那条路径上
插件 delegate 给 `llm-retry`，后者按自己的策略重试。这次不改变该行为（用户明确说
"我自己手动把 dsh 的重试次数调高点"），但它决定了删掉总上限后仍有的边界：没勾的码
由 DSH 收尾。

## Decision

1. **配置词汇改成重试次数**：`candidates[].maxRetries`（0..99，默认 0）与
   `chain.firstHopMaxRetries`（0..99，默认 0）。首发不计入。
2. **删除 `chain.maxTotalAttempts`**，从 schema、类型、决策层、UI 与公式一并移除。
   一个 step 的花费上界 = Σ(每条候选的 `maxRetries + 1`)，不需要第三个数字。
3. **决策层仍然按"调用次数"工作**，`resolveChain` 是唯一的换算点（`maxRetries + 1`）。
   为什么不让 `planFire`/`decide*` 也改说重试：它们数的是真实发火次数，`attemptsOnCandidate`
   与 `maxAttempts` 的比较是这条不变量本身；把 +1 散进三个决策函数只会让下一轮读者
   重新数一遍。
4. **旧配置就地迁移**：schemastery 保留未知字段（实测），旧记录会同时带
   `maxAttempts` 与 schema 补上的 `maxRetries: 0`。所以迁移以**旧键是否存在**为准，
   不看值——否则一个配了 3 次调用的候选会被静默降成"不重试"。首次从界面保存后旧键
   自然消失。
5. **不改变未勾选失败码的归属**：插件不切换它们，由 DSH 按自己的策略重试并收尾。
   总上限删除后这是唯一不由插件控制的路径，已写进 README 与 UI 提示。

## Alternatives considered

1. **保留总上限，只把它的文案改成"可选刹车"。**
   - 最强的理由：它确实能在长链上限制一次请求的花费，且删除要动 schema、迁移、UI 与
     全部组合场景。
   - 为何被否：用户的原话是"完全没用还让人搞半天不知道是干啥的"。它从不切换、从不
     增加调用，唯一效果是省调用数；而"一次请求最多打几次"在每条候选已经独立配次数的
     情况下可以自己求和。保留一个只会截断的第三个数字，就是保留用户这轮困惑的源头。
2. **只改 UI 文案，配置仍存"调用次数"（0 显示成 1，内部 -1）。**
   - 最强的理由：零迁移、零行为变化，半小时能上。
   - 为何被否：配置、日志、README 与 DSH 的 `maxRetries` 会永远差 1；下一轮任何直接
     读配置的人（包括宿主日志与热更新校验）都要重新学一遍。这个项目已经把"两套词汇
     靠注释对齐"记为反复出现的事故形状。
3. **让插件自己执行重试，填 10 就打 11 次。**
   - 最强的理由：这样插件填的数字才真正说了算，不再受 provider 策略限制。
   - 为何被否：那意味着自己实现退避、取消与 durable 记录，与 `llm-retry` 形成两套
     重试引擎，两条账会立刻开始打架；而"绝不盲重试"（无退避的同路由重试）正是本项目
     从第一天就拒绝的行为。保留现状 + UI 明说"实际次数受 DSH 策略限制"更诚实。
4. **把未勾选切换的码也纳入候选次数（堵洞）。**
   - 最强的理由：这样"每条候选重试几次"对所有失败码都成立，模型完全自洽。
   - 为何被否：用户明确要自己调 DSH 的重试次数，并把它当刹车；插件去否决一条"用户说
     不要切换"的路径上的重试，等于替用户决定何时放弃。本轮不动，留作未决项。

## Consequences

- 配置字段改名，旧配置经 `effectiveChain` 迁移（`maxAttempts - 1`，`firstHopMaxAttempts - 1`），
  行为逐字不变：旧配 2 的候选仍是 2 次调用。
- `decideAfterInner` 不再否决内层重试（没有上限可执行）；`decideRecovery` 与
  `decideBeforeInner` 删掉总上限判断，边界改为"末位候选 + 各自的次数"。
- 组合场景 `budget-cap-when-the-whole-chain-dies` 改名 `chain-exhausted-two-candidates`；
  `total-cap` 改写为 `retries-bounded-by-the-provider-policy`；`veto-rejects-llm-retry-…`
  删除（否决分支不存在了）。
- UI：步进器改成"失败后重试"（0..99），预算分区改成只读的"一次模型调用最多 N 次真实
  调用"，并写明实际次数受 provider 策略限制。
- 一个新的真实边界浮出水面：插件填的次数超过 provider 的 `maxRetries` 时，多出的部分
  不会发生。默认 provider 策略是 5，所以 0..5 的配置仍然精确。
