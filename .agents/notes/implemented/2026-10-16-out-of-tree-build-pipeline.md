# Agent Note: 树外包自复刻 DSH 构建管线——单段式 tsdown + package 模式 Typert

Status: implemented

## Problem

插件长期是手写单文件、无构建步骤，`exports` 直指 `src/`。agent 据此推断出一条
没写下来的假限制："这个包不参与 DSH 的构建契约"。后果是插件自有 Remote 的注册
通道根本不存在——`dsh-typert-loader` 跳过没有 `./typert` 导出的包，主动探测档位
只能在 UI 里禁用加说明。需要写下的是：树外包怎样在不改 DSH 的前提下获得
sanctioned 的构建与 Typert 通道，以及 DSH 的哪些内部件不能引、为什么。

## Decision

本包自复刻 `clientBundle` 的构建契约（不引 DSH 未发布的预设）：tsdown 单段式从
TypeScript 源打包 Node 半包，`typertPlugin({ mode: 'package', faces: ['host'] })`
只发本包 host face，workspace 根由项目根自建的 `tsconfig.host.json` 标记，
`@typert` 表面落在 `Profile` 上。

准入门槛（可机械判定）：

1. 四件套存在且被 loader 认到：`npm run bundle` 后 `lib/index.js`、
   `lib/types/index.d.ts`、`lib/typert.host.js`、`lib/typert.host.d.ts` 均在；
   从 profile 配置树根（cordis.yml 目录）`createRequire.resolve('dsh-model-router/package.json')`
   → `exports['./typert'].default` → `import` → loader 的 `validateTypertManifest`
   通过（实测：package=dsh-model-router、face=host、schemas=Profile、invocations=0）。
2. 包内 node_modules 无运行时依赖副本：`packages/dsh-model-router/node_modules`
   下不存在 `zod`、`@deepseek-ai/schemastery`、`@deepseek-ai/cordis`、
   `@deepseek-ai/dsh-llm`、`@deepseek-ai/dsh-agent`（安装带 `--legacy-peer-deps`，
   peer 一律由宿主树解析）。
3. 生成物零手写：`lib/typert.host.js` 首行是
   `Generated by @deepseek-ai/dsh-typert-generator`，且 `lib/` 进 `.gitignore`，
   仓库不提交生成物副本。
4. `dsh --profile web --dump-config` 出现 `id: model-router` 行，启动无
   typert-loader 聚合报错。

## Alternatives considered

1. 从 DSH checkout 相对路径引 `clientBundle`（`import { clientBundle } from '../../client/tsdown.client.ts'`）
   - 最强的理由：与 DSH 包内写法逐字一致；预设自动处理 externals、CSS 管线与
     工厂封装，DSH 改预设能同步受益。
   - 为何被否：预设不在任何已发布包里——DSH cookbook 明说仓库外的包要自己复刻
     这一步构建（`docs/cookbook/adding-a-settings-card.md:60`）；其辅助模块读
     monorepo 相对路径（`./modules/src/client/manifest.ts`、`./web/src/platform.ts`、
     `../../scripts/*`），树外引它等于把构建绑死在一台机器的 checkout 路径上，
     交付与 CI 不可复现。
2. 两段式（对齐 monorepo 根：`tsc -b` 先发 `lib/types`，tsdown 消费 JS）
   - 最强的理由：与 DSH 根构建同构；`clientBundle` 的 client 入口就是
     `lib/types/client/index.js`，sourcemap 链自动接。
   - 为何被否：两段式的收益（composite 项目图驱动全仓按依赖序构建）只在多包
     workspace 里存在；单包树外复刻要自建项目图，纯增失败面。JS 由 tsdown 直接
     从 TS 源打包，tsc 只发声明（`emitDeclarationOnly`），落点与两段式一致。
3. 手写 typert manifest 绕过生成器
   - 最强的理由：零构建依赖，立即可得 `./typert`。
   - 为何被否：方案硬约束是必须用 DSH sanctioned 机制；loader 的
     `validateTypertManifest` 逐字段校验，手写件与生成器演进必然漂移。
4. 表面挂在 cordis Context augmentation 上
   - 最强的理由：更贴近 cot-translation 的 `TypertRemoteService` 先例，Phase 3
     的 `RouterHealthService` 本来要走这条。
   - 为何被否：Phase 1 插件是函数形态、不提供任何 Cordis service；
     `collectServices` 要求 Context 键解析到本包导出的 class/interface，为尚不
     存在的 service 补空壳类就是假表面。等 Phase 3 类落地时再开真表面。
5. 表面挂在 `Candidate`，避开 `Strategy` 的 indexed-access
   - 最强的理由：零类型改动——`Candidate` 全 Plain JSON，Zod 发射器直接吃。
   - 为何被否：`Profile` 才是插件的中心业务类型（一条完整路由规则），只反射
     `Candidate` 消费者拿到半条规则没有用处；且 `Strategy` 改显式联合 +
     `readonly Strategy[]` 注解是编译期同源的两行类型改动，顺带消掉 Typert
     不支持的 indexed-access 节点。

## Consequences

- 收益：`./typert` 通道真实存在（loader 解析链实测通过，boot 无聚合报错）；
  exports 指向构建产物，交付形态与 DSH 包一致；管线成为 Phase 3 Remote 的前置
  地基；devDependencies 不再与 peerDependencies 重复——重复会让我装进包内的
  @deepseek-ai 副本遮蔽运行时解析。
- 代价：开发循环多一步 `npm run bundle`（改源码后必须重建才在浏览器生效）；
  包内多一份 node_modules 与 package-lock.json（tsdown/rolldown/oxc/
  typescript/生成器）；typescript 双版本并存——包内 v6（classic，生成器需要
  编译器 API）供 `bundle`，项目根 v7（native preview）供 `npx tsc` 检查；
  构建配置自复刻，DSH 预设将来的演进不会自动流进本包，需人工对照。
