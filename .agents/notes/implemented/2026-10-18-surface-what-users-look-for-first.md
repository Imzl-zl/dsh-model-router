# Agent Note: 可见性、主操作位置与弹窗容量按「谁在找什么」重新分配

Status: implemented

## Problem

UI 审查（`docs/design/ui-review.md`）列出的剩余七条不是七个独立瑕疵，它们共同指向一件事：**界面的层级顺序与用户的查找顺序不一致**。

- 用户想知道「这条链有没有配识图」，只能逐个展开节点的 ⚙️；
- 用户从健康页看到某条渠道异常，想知道「它在哪条链里、排第几」，只能读一串不可点的静态文本；
- 用户改完一个数字，唯一的保存按钮在屏幕最顶上，隔着几百像素的编辑区；
- 用户想删掉一条链，删除按钮却占据页头主操作位，而真正常用的「添加候选」在整页最底部；
- 用户打开「健康设置」想改熔断规则，得先穿过两个 Tab、四块 Tier 和一段一次性调优的探测内容覆盖。

共性：**高频、轻量的动作（看一眼、跳过去、保存）被放到了深处，低频、破坏性的动作（删除、改熔断规则）却占据了显眼位置。**

## Decision

按「这件事被查找的频率与它当前的可见度」重新分配位置，破坏性动作下沉、诊断性信息上浮、保存动作复制到当前视口。

准入门槛（可机械判定）：

1. **状态可见即入口**：一条链若存在带图片条件的候选，页头必须有一个可点的 `🖼️ 识图路由` 徽标，点击展开第一个满足条件的节点。判定：`chain.ts` 里有 `firstImageIndex` 计算且渲染 `imageRouteBadge`；`CandidateNode` 用 `useEffect` 跟随 `props.imageFocus`。
2. **每块观测数据都能跳回它的配置处**：健康页的用途徽标必须是按钮且调用 `onJumpProfile`。判定：`workspace.ts` 里 `channelUsageBadgeButton` 是 `h('button', …)`，`page.ts` 传 `onJumpProfile`，跳转前清 `focusRoute`。
3. **保存动作在视口内**：有未保存改动时，工作区底部出现保存/放弃条。判定：`chain.ts` 渲染 `dirtyBar`，条件为 `props.dirty && !props.saving`，复用 `props.onSave` / `props.onDiscard`，不新增状态。
4. **破坏性动作不占页头主操作位**：删除只出现在 `policies` 页签底部的 `dangerZone`。判定：`workspaceHeaderCard` 右侧只剩默认池开关；`chain.ts` 里 `onDeleteProfile` 只被 `dangerZone` 引用。
5. **弹窗一站一件事**：熔断规则行编辑器移入独立 `BreakerRulesModal`，主弹窗熔断 Tab 只留开关、摘要与管理入口。判定：`modals.ts` 存在 `BreakerRulesModal`；主弹窗熔断 Tab 不含规则行输入框；规则状态仍由主弹窗的 `useState` 持有，子弹窗只收 `rules` 与 `onChange`。
6. **同角色按钮只有命名档位**：调用点不得就地改尺寸。判定：无 `Object.assign({}, S.catalogBtn`；`catalogBtn` / `addProfileBtn` 已删除。

## Alternatives considered

1. **把识图配置整体提升成第三个一级页签**
   - 最强的理由：彻底解决发现性，识图是三能力里最需要被知道的，给它一个独立入口比一个徽标有力得多。
   - 为何被否：图片条件在数据上属于**单个候选**（`candidate.needs`），不是链级别。提升成页签要么把「哪个候选」摊平变成一列表格，要么在页签里再选一次节点，等于把现有展开面板搬个家、多一层导航。徽标 + 精准展开已经在正确的粒度上。

2. **健康页的用途文本改成默认可点的链接样式**
   - 最强的理由：可点性最强，用户一眼知道能跳。
   - 为何被否：渠道卡一行最多可能挂三四个用途徽标，全做成链接色会让一屏文本里出现一片蓝色，把真正的诊断信息（状态药丸、探测徽标）压下去。默认外观保持静态、只加 `cursor` 与 hover 变化，可点性由光标和 `title` 承担。

3. **保存条常驻，只在有改动时高亮**
   - 最强的理由：位置固定，用户永远知道保存按钮在哪，不用猜它什么时候出现。
   - 为何被否：常驻意味着没有改动时也占 40px 高度，而工作区本来就紧。顶栏已经有一个永久的保存按钮，底部这条的职责就是「此刻你改了东西」这一件事——出现本身就是信号。

4. **熔断规则按审查建议从 `policies` 页进入，彻底脱离健康设置**
   - 最强的理由：熔断规则的语义确实更靠近链路配置，而不是健康采集；从 `policies` 进入用户在改路由时顺手就能设置。
   - 为何被否：熔断与健康采集共享 `health.breaker` 这一段配置和一个总开关，拆到两个入口会让「开关在这、规则在那」的困惑取代「都挤在一起」的困惑。你选定的方案（同弹窗、编辑器独立）保留了两者的语义关联，只解决了容量问题。这个方向可以在熔断体量继续增长时重新评估。

## Consequences

- 收益：三条诊断路径（看图路由、跳回链、就地保存）从「要走三步」变成「一步」；删除从页头主操作位下沉到策略页，误触面小了；熔断规则编辑器获得独立弹窗的完整宽度，四列规则行不再挤在主弹窗的滚动区里；按钮尺寸从两处就地覆盖收敛成两个命名档位。
- 代价：`ChainView` 在一次重写中从单棵嵌套表达式改成「先建区块变量、再组装」，文件变长但结构可读；新增了两个可点元素（识图徽标、用途徽标）与一条条件渲染的保存条，交互面比之前宽。`breakerTier` 与 `inspectTiers` 改为变量后，主弹窗的渲染顺序不再由 JSX 嵌套位置隐式决定，读代码时需要顺着变量名找。重构过程中还发生了一次真实的回归（规则写入退回闭包形式、`disabled` 未透传），两处都由既有守卫用例当场拦下——说明这两条守卫的形状是对的，但也说明拆分弹窗时容易漏掉 props 透传。
