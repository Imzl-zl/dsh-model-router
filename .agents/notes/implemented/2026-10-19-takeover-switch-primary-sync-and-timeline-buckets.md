# 接管开关、主模型同步与时间轴桶化（2026-10-19）

> **部分被同日 `2026-10-19-one-global-fallback-chain.md` 取代**：主模型、`primaryProfileId`、
> 按模型分规则（`profiles`/`when`）与「写 DSH 默认模型」的同步已删除。本篇的接管开关
> （默认关）、时间轴时长桶、吞吐拆分、整卡拖拽与名字截断仍然有效。

## Context

用户装好插件后第一次使用就提出四类问题，全部指向"装了就直接生效、而生效的语义说不清"：

1. 路由什么时候接管？装完就直接用了？有没有开关？开启后是不是该自动把模型改成主模型？
2. 刚配置上健康状态就显示了，这正常吗？"近期记录 14"是多久的？这么多格背后肯定有个时间轴。
3. 吞吐不对——探测端点没有正式输出，就没有 token 输出，也就没有吞吐。
4. 模型名一长就挤压；换位置必须拉着前面的几个点，不能整块拖着走。

源码核查后的根因，四条里三条是缺陷而不是误解：

- `config.enabled` 默认 true，而 `apply.ts` 的 `onEnabled` **从来没被 page/footer 传过**——顶栏"● 路由生效中"是一枚不可点的徽标。所以"没有任何确认步骤，建好规则的模型立刻被接管"。
- 时间线是"最近 24 次观测、一格一次调用"（`MAX_TIMELINE_POINTS = 24`），跨 20 个会话合并。一格不是一段时间，24 格可能横跨几天；可用率是 healthy/观测数，不是时间加权。
- 紧凑徽标把"探测首字 140ms"和"被动 161.1t/s"印在同一行，看着像同一次测量。探测只测首字（`probe.ts` 拿到第一个内容字节就 abort），没有吞吐。
- `draggable` 只挂在 20px 握把上。

## Decision

四项用户决策（逐条确认，未替用户决定）：

| # | 决定 |
|---|---|
| D1 | 新增可见的「接管路由」开关；开启时把 DSH 的新会话默认模型写成主模型，且主模型变化时跟随 |
| D2 | 主模型 = 显式标记为「主」的那条规则（`primaryProfileId`），默认第一条；标记悬空时回落第一条 |
| D3 | `enabled` 默认改为 **false**——新装不再"装完就接管" |
| D4 | 时间轴 24 格固定 + 桶长可配（1/5/10/30/60 分钟，默认 10 分钟 = 4 小时窗） |

实现要点：

- **同步走 DSH 自己的 `agentDefaultModel`**。这是唯一能让"开启接管后新会话从主模型开始"为真的机制：`agentDefaultModel.currentSelection()` 只在会话没有 request header、没有 pending pick 时被读（`api/session-controller/src/agent.ts:299-304`），所以写它影响的恰好只有新会话，运行中的会话留在自己的 header/pick 上——正是用户描述的"DSH 自己那套策略"。
- 同步只在**值不同时**写，且保留已配置的 reasoningEffort（`saveSelection` 换的是整个 config 对象，不带 effort 就会把用户配的档位悄悄抹掉）。
- 同步跑在每次 fiber 启动（含配置保存后的重启），所以"开启接管"与"换了主模型"共用一条路径，不需要第二条更新通道。
- 关闭接管**不还原**默认模型：还原是用旧决定覆盖用户此后手动选过的模型。
- 时间轴改为**固定格数 × 时长桶**：`bucketTimeline()` 把观测点按时间戳分进 24 个桶，柱高 = 成功率（healthy 计 1、degraded 计 0.5、unhealthy 计 0），颜色按 ≥99% / ≥90% / <90% 分档，空桶画贴底虚线槽读作"无数据"。观测点按时间戳保留 24 小时 + 600 条上限，所以改桶长是重新分格而不是重新采集。
- 拖拽从整张卡发起，`dragstart` 里对 `button/input/textarea/select/a/[contenteditable]/[role=tabpanel]` 一律 `preventDefault`——那些地方一拖就该是它们自己的行为。
- 模型名统一为"可压缩 + title + 中间省略"（`shortModelName`）：网关渠道的模型 ID 常常是一整段 UUID，末尾截断会把它变成"前 12 个十六进制"，同一网关下一堆模型共用前缀，截出来全都一样。

## Alternatives considered

### A1. 接管开关默认开，只是把它做出来

**最强理由**：与现状一致，用户不会被"插件突然不工作了"吓到；`enabled` 一直是 true，改成 false 对存量配置是一次静默行为变化。

**为何被否**：用户明确问的是"我安装完直接就用了？是不是应该有个开启关闭接管？"——他要的是默认不接管。且接管会改请求实际打到的渠道，这是有资金与限流后果的副作用，默认值必须是用户显式选择。存量配置里已存 `enabled: true` 的不动（schema 默认值只在字段缺失时生效），受影响的只有新装。

### A2. 自动同步默认模型，但只在开启/保存时同步一次，不跟随主模型变化

**最强理由**：写入次数最少，最不容易和 DSH 的 HMR 互相触发；"不跟随"也意味着插件不会在用户背后反复改全局配置。

**为何被否**：用户选的是"要，且跟随"。而且不跟随会立刻产生一个说不清的状态——主模型明明换了，新会话还停在旧模型上，而界面上没有任何痕迹。跟随的代价（见 Consequences）用"只在值不同时才写"压到接近零。

### A3. 不自动同步，只给一个一键「设为新会话默认模型」

**最强理由**：完全不碰 DSH 的全局配置，没有"插件在背后改了我的默认模型"这类意外；也避开了写入被 overlay/home patch 拒绝时的失败路径。

**为何被否**：用户要的是开启即生效。而且每次新建会话都要手动点一次，这个产品就不成立。被否的不是"显式动作"本身——它作为「重新同步」按钮保留了下来，因为 DSH 每次手动换模型都会把默认改掉，用户需要一个把默认拉回来的手段。

### A4. 主模型 = 永远是列表第一条，靠侧栏排序切换

**最强理由**：不加新状态、不加新 UI；"第一条"本来就已经是候选链的起点语义。

**为何被否**：用户选了显式标记。第一条同时是"候选链起点"和"新会话默认模型"两个语义时，用户改排序会顺带改掉新会话从哪开始，而这两个决定本该分开。显式标记让"谁是主"在列表和详情页都看得见。

### A5. 时间轴格数与桶长都可配

**最强理由**：最灵活，想看的窗口完全由用户定。

**为何被否**：用户选了"24 格固定 + 桶长可配"。格数可配会让同一屏有时 6 格有时 48 格，而 24 格 × 1~60 分钟已经覆盖 1 小时到 24 小时；再往下是把显示密度问题推给用户。

### A6. 每格一次观测（现状），只是把 24 改成可配

**最强理由**：实现不动，数据模型不动，没有迁移。

**为何被否**：它治不了病根——一次观测就是一次真实调用，而调用在时间上不均匀。一天调两次的链和一分钟调两次的链画出同一张图，24 格既可能是十分钟也可能是三周。用户要的是"某个时间段不行可能又行了"，那是一段时间的成功率，不是一串事件。

### A7. 自建一套指针事件拖拽

**最强理由**：触屏也能用，且拖影、自动滚动都能自己控。

**为何被否**：HTML5 拖放已经处理了拖影、放置目标与滚动容器内的自动滚动，自建一套要把这些重做一遍。代价是触屏仍然不可用，但上下按钮一直在，且本次只解决"必须抓着那几个点"这个问题。

## Consequences

**收益**

- 接管从"装完即生效"变成显式选择，且开启后新会话自动落在主模型上；旧会话按 DSH 自己的规则不动。
- 主模型在列表与详情页都有标记，"谁是主"不再靠猜。
- 健康时间轴有了时间轴：一格是一段时间，高度是该桶的成功率，颜色分档，空桶是无数据；桶长可配，改桶长不丢历史。
- 探测与被动指标分开表述，吞吐只在有真实输出时出现，并说明它是端到端速率而非解码速率。
- 整卡可拖（控件除外），长模型名不再把徽标和控件挤出卡片。

**代价**

- **DSH 每次手动换模型都会覆盖默认**（`commands.ts:177`）。所以自动同步可能被一次手动选择静默打掉——插件不重写、不重试，只把状态显示出来（已同步 / 已被手动选择更改 / 写入失败 + 重新同步）。这是有意的：在每个请求上重断言等于和用户自己的选择打架。
- **开启时会写 DSH profile 的 `cordis.patch.yml`**。这会让 DSH 的 HMR 多重启一次；因为只在值不同时写，之后启动不再写。被 overlay 或 home patch 覆盖时 `configEditor.edit` 拒绝，插件 `logger.warn` 响亮报告而不是静默（`config-editor/src/index.ts:139-140`）。
- **投影里的观测点从"24 条"变成"24 小时内最多 600 条"**，持久化体积上升；`stateVersion` 未动（schema 不变，旧行按原样读入后由新规则裁剪）。
- 默认值从 true 改成 false 是一次行为变化：新装后不建规则、不开开关，插件完全不动作。
- 触屏仍不能拖拽。
- 时间轴柱高编码成功率后，"全红/全绿"的旧读图方式作废，需要图例；图例因此进了工作台头部与每张卡片。
