# 健康大盘的渠道清单丢了"配置的那一半"（2026-10-19）

## Context

用户问："还有这个模型健康是所有配置的还是你咋获取的？"

他去看了代码会发现答案不是他预期的：**渠道清单读的是 `draft.profiles` 和
`draft.default`**——而这两个键在单链化之后已经不存在了。整段是死代码，于是配置的
降级候选一个都不进大盘。

后果不是"少显示一行"：新加的候选**既不能连通性检查也不能探测**（大盘里没有它，
那两个按钮挂在卡片上），用户只能看着一堆"用过的"渠道，以为自己没配。

## Decision

**清单的来源改成一条规则写清楚**：`draft.chain.candidates`（配了的降级候选）∪
被动观测过的路由 ∪ 发现结果 ∪ 探测结果。

第一跳**故意**不在"配置的那一半"里：它是用户在 DSH 里选中的模型，插件在请求到
来之前不知道是哪个，所以它只能在被观测过之后出现。这是形态决定的，不是漏了。

连带三处清理，都是同一批单链化留下的：

1. `props.onJumpProfile(u.name)` 调用一个**不存在的 action**——按规则跳转随规则
   一起删了，单链之下"这条渠道被哪条规则用"没有第二个答案。改成静态位次徽标
   （`降级链第 N`），不再做成按钮。
2. 字典里 `channelUsedIn` **重复定义了两次**（`用于 {n} 条规则` 和 `被以下规则使用，
   点击跳回：`），后者静默覆盖前者。两个都删，换成 `channelUsedInChain` /
   `channelUsedInChainTip`。
3. `channelUsageBadgeButton` 样式与 `.dsh-router-usage-jump` 注入规则成为死代码，
   删除。

## Alternatives considered

### A1. 只把 `draft.profiles` 换成 `draft.chain.candidates`，别的不动

**最强理由**：一行改动，用户的问题就答上了。

**为何被否**：跳转按钮调用的 action 不存在，点一次就是 TypeError；字典重复键会让
下一个读代码的人以为还有"按规则跳转"这回事。三处是同一个根因（单链化没改完），
只改一处等于把另外两处留给下一个人。

### A2. 让第一跳也进清单（用 `agentDefaultModel.currentSelection()` 读当前选中）

**最强理由**：用户会想"我选中的模型怎么不在大盘里"。

**为何被否**：那正是单链化明确删掉的依赖——插件不读、也不写用户的默认模型选择。
而且请求没来之前读到的"当前选中"随时会变，大盘显示一个可能已经不算数的渠道比
不显示更糟。它被观测过之后自然会出现。

### A3. 大盘只显示配置的候选，不显示观测到的

**最强理由**：清单稳定，不随历史增长。

**为何被否**：观测到的历史正是健康监控的价值——一条已经不在链里但昨天还在用的渠
道，它的记录仍然说明"这条渠道本身好不好"。现在的形态（配置 ∪ 观测，用徽标区分）
两个问题都答上了。

## Consequences

**收益**

- 配了就进大盘，新候选可以立刻被检查/探测。
- 三个死代码/坏接线清除，字典不再有重复键。
- 位次徽标直接说清"它是第几个被尝试的"——比原来的"用于 N 条规则"更贴合单链。

**代价**

- 第一跳仍然不在"配置的那一半"（见 A2），只能被观测后出现。用户可能再问一次。
- 徽标从可点变成静态文本，少了一个跳转入口——但那个入口本来就会抛。

## 验证

- 新增显示层回归（真实构建产物 + 真实 `RouterPage`）：两个"配了但从未被调用"的
  候选必须都出现在渲染树里，且空状态不得触发。**抽样验证**：把来源改回读
  `draft.profiles` 立刻转红（`the configured candidate must reach the dashboard`），
  恢复即绿。
- unit **144**、client-controller **51**、run.mjs **23 场景 0 失败**、remote **15**、
  bundle / tsc / `node --check` 全过；DSH checkout 0 行。
- 全仓扫过 `onJumpProfile` / `channelUsedIn` / `channelUsageBadgeButton` /
  `dsh-router-usage-jump`，均无残留引用。
