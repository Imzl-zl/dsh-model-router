# Agent Note: 连通性检查的 deadline，与"读不到"不等于"没有"

Status: implemented

## Context

两件事在同一轮被确认，症状不同、病灶相同：**一条没人等的路径被当成了一条没有事的路径。**

1. **连通性检查没有 deadline。** 2026-10-17 的浏览器实测就记下了：这条路只接受取消、
   不设超时。一个"接受 TCP 但永不应答"的端点会让宿主那侧的 `Promise.all` 永不结算，
   浏览器侧的 `ui.checking` 因此永久为真；`checkAll` 第一行是 `if (ui.checking) return`，
   于是之后的手动检查与定时巡检全部 no-op，只能刷新页面恢复。2026-10-20 的审查把它
   重新登记为「仍未修」——它是当时唯一一个会让整个健康监控功能失效的缺陷。
2. **健康历史读取失败被静默吞掉。** `loadPassive` 用 `.catch(() => null)` 逐会话吞、
   外层再 `.catch(() => {})` 吞一次。投影读不到时页面照常渲染成「未调用 / 未探测」，
   与"这条渠道真的没跑过"在屏幕上完全一样。这正好踩在仪表盘自己的承诺上：它的全部
   工作就是报告渠道做过什么。

两条都不缺复杂度，缺的是一次把"没有答案"和"答案是空"分开的决定。

## Decision

1. **一个共用的 deadline 融合点**（`src/deadline.ts` 的 `fuseDeadline`）：一个
   `AbortController` 同时承载"调用方取消"与"自家超时"；`expired()` 只在自家定时器
   真的先触发时返回真；`whenExpired` 让调用方在适配器忽略 signal 时也能结算。
   `probe.ts` 迁到它，原先手搓的融合与私有 `TimeoutError` 一并删除——同一个事实不再
   有两份表达。
2. **连通性检查每条路由 10 秒硬上限**（`CONNECTIVITY_TIMEOUT_SECONDS`），超时判
   `unreachable` + `TIMEOUT`，与探测的 deadline 同一档。宿主仍是 `Promise.all` 扇出，
   但现在每条都必然结算：一条慢渠道不会拖住其余渠道的答案。
3. **竞速，而不是"abort 一下继续等"**：`Promise.race([discoverModels(...), whenExpired])`。
   abort 只是请求适配器停手，竞速才保证宿主这一侧无论适配器是否听话都会结算。
4. **`ui.passiveError`**：会话列表被拒、或 N 个会话里有的投影读取被拒，都折成一条可见
   警示（带原因与失败计数）；整次读取干净时清空。它渲染在健康页标题下，点用
   `dsh-router-health-warning-dot`（`dsh-router-dot` 仍被源级守卫要求"每行只有一个"）。
5. **文案带占位符校验**：`healthHistoryUnreadable` / `healthHistoryPartial` 必须含
   `{error}`（后一条还有 `{failed}` / `{total}`），少一个，原因就永远不出现在屏幕上。

## Alternatives considered

1. **只 abort，不进 race。**
   - 最强的理由：最少代码，且绝大多数适配器都尊重 signal，超时后立刻会以 `ABORTED`
     结束——多一个 race 像是在防一个不存在的敌人。
   - 为何被否：不尊重 signal 的适配器不是假想敌，而是"任何第三方 provider 包"的默认
     可能。一旦出现，症状与修之前一模一样（UI 永久转圈），而且更难查——因为日志里
     明明有一条 deadline。宿主侧的结算是这条修复的不变量，不能建立在适配器的善意上。
2. **把超时做成每条路由可配的字段。**
   - 最强的理由：不同网关的清单接口快慢差很多，用户可能真的知道自己的端点慢。
   - 为何被否：用户在这里没有可决定的东西。一个要 30 秒才回模型清单的网关就是坏网关，
     给它一个更长的等待只会让"检查"变成"陪着等"。常数 + 一句说明足够。
3. **超时判 `unavailable`（"没能检查"）。**
   - 最强的理由：`unavailable` 的既有定义是"检查没能跑起来"，而一次被放弃的检查确实
     没拿到答案；UI 对它是灰色的 unknown，不会冤枉渠道。
   - 为何被否：检查确实跑了、端点确实在这段时间里没答——这是渠道自身的事实，与探测
     的 `TIMEOUT` 是同一个判定。判成 unknown 会把一个用户可修的问题从屏幕上抹掉，
     而那正是这次要避免的失败模式。
4. **浏览器侧再加一层看门狗。**
   - 最强的理由：`ui.checking` 是在浏览器里锁死的，就地兜底最直接；将来任何宿主回归
     都不会再冻住界面。
   - 为何被否：同一事实两处表达。宿主已经保证结算，客户端再加一层只会掩盖宿主回归，
     并且让"到底谁在等谁"多一个答案。真正的回归应该让测试红，而不是被兜底吞掉。
5. **读失败只写 `logger.warn`，界面保持空表。**
   - 最强的理由：健康历史是辅助信息，读不到时不该用一条红字打扰用户；日志已经足够
     给维护者看。
   - 为何被否：这条提示的价值就是让用户知道"你看到的空不是真的空"。写进日志等于对
     用户隐瞒，而隐痕恰好发生在这个页面最核心的承诺上。

## Consequences

- 收益：一个坏端点不再能让整套监控停摆；「历史读不到」与「没有历史」在屏幕上可分；
  探测与连通性检查现在共用同一个 deadline 形状，下一轮只改一处。
- 代价：10 秒是拍的，没有真实网关清单延迟分布支撑——偏慢但健康的端点会被判一次
  `unreachable`（`TIMEOUT`），用户重跑一次即可，但这一下的噪声确实存在。
- 代价：race 之后被放弃的那次发现请求仍在后台跑到适配器自己结束；适配器通常收到
  abort 立刻收尾，但如果它完全不看 signal，就是一个悬挂请求，直到进程退出。
- 代价：`ui.passiveError` 是新的界面状态，本轮只跑了四套件（unit 152 /
  client-controller 53 / run 22 / remote 15 / tsc 0），**没有在真实浏览器里点过**。
  下一次动健康页时应先补这一项。
